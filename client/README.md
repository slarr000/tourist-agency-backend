# Tourist Agency Client

Frontend внутренней информационной системы туристического представительства IS Tour. Лендинг ведет в рабочую панель сотрудников для управления туристами, операциями и отчетами.

## Основные возможности

- Лендинг внутренней информационной системы
- Публичный лендинг и административная панель, защищенная входом сотрудников
- Cookie-сессия администратора с автоматическим выходом по истечении срока действия
- CRUD туристов с расширенной формой личных и паспортных данных
- Поиск и фильтры по категории и семьям; просмотр связей «родитель — ребенок» в карточках туристов
- Отдельная панель склада: прием груза, весовые и отправочные ведомости, маркировка, бирки, фактический/объемный вес, упаковка, страховка и этапы обработки
- Административный CRUD справочников и операций: гостиницы, рейсы, агентства, экскурсии, бронирования, финансы, документы и поездки
- Центр отчетов по пунктам 1–15 ТЗ и дополнительные отчеты
- Экспорт сформированных отчетов в CSV
- Поддержка работы с backend API через единый слой запросов
- Адаптивный интерфейс со светлой и темной темами, сохранением выбора, анимированными переходами, карточками разделов и учетом настроек reduced motion

## Быстрый запуск и демонстрация

### 1. Подготовьте PostgreSQL

В pgAdmin откройте базу `Touristic Firma`. Один раз выполните SQL-файлы в таком порядке:

- `../Database/StoredProcedures.sql` — функции базы данных;
- `../Database/DemoData.sql` — первоначальная тестовая группа;
- `../Database/DemoDataSupplement.sql` — дополнительные группы и записи для отчетов;
- `../Database/CourseworkEnhancements.sql` — привязка финансов к группам, каталог путевок, функции отчетов и процедура их вызова;
- `../Database/CourseworkSampleData.sql` — большой набор синтетических данных для демонстрации (300 туристов и связанные записи).

Демо-скрипты добавляют синтетические записи, не удаляют реальные данные и безопасны для повторного запуска. Если скрипты уже запускались, повторно выполнять их не обязательно.

Если база уже настроена, для добавления большого набора откройте в pgAdmin базу `Touristic Firma`, выберите **Tools → Query Tool**, откройте `CourseworkSampleData.sql` и выполните его (**F5**). Скрипт создает 300 вымышленных туристов и связанные рейсы, гостиницы, паспорта, бронирования, поездки, экскурсии, груз и финансовые записи. Он не использует реальные персональные данные и при повторном запуске пропускает набор.

Если база настроена ранее, повторно выполните `StoredProcedures.sql` и затем `CourseworkEnhancements.sql`, чтобы установить процедуры `CALL`, используемые текущей версией backend. Первый скрипт также создает отдельную таблицу `employee_accounts` и процедуры для проверки пароля и создания учетных записей сотрудников. Последняя версия `CourseworkEnhancements.sql` включает проверки совершеннолетия сопровождающего, учет детей в бронированиях экскурсий, этапы обработки груза («Принят на склад», «Упакован», «Готов к отправке», «Отправлен») и месячный финансовый отчет. Для уже подготовленной базы эти скрипты можно выполнить прямо в Query Tool; изменения схемы аддитивны.

Чтобы полностью заменить демонстрационные данные, сохранив учетные записи сотрудников, сначала сделайте резервную копию БД, затем выберите `Touristic Firma` в pgAdmin и выполните `../Database/ResetAndSeedDefenseDemo.sql`. Скрипт проверяет имя базы, удаляет строки из всех таблиц схемы `public`, кроме `employee_accounts`, сбрасывает последовательности и загружает новый согласованный набор синтетических данных. Удаление и заполнение выполняются одной транзакцией: при ошибке изменения откатываются. Скрипт не удаляет таблицы, процедуры или учетные записи сотрудников.

Создайте отдельную учетную запись каждому сотруднику через pgAdmin Query Tool, подставив индивидуальные логин и пароль:

```sql
CALL public.app_create_employee_account_proc('employee1', 'ЗаменитеНаСвойНадежныйПароль');
```

Пароль для новой учетной записи должен содержать от 1 до 6 символов. Короткий пароль слабее и подходит только для демонстрационной системы в доверенной локальной сети. Выполните команду отдельно для каждого сотрудника; не сохраняйте реальные пароли в SQL-файлах или системе контроля версий. Самостоятельной регистрации посетителей в приложении нет. Уже созданные учетные записи с более длинным паролем сохраняют возможность входа.

### 2. Запустите backend

Откройте первый терминал и введите:

```bash
cd ..
read -rsp "Пароль PostgreSQL: " DB_PASSWORD; echo
export ConnectionStrings__DefaultConnection="Host=localhost;Port=5432;Database=\"Touristic Firma\";Username=postgres;Password=$DB_PASSWORD"
unset DB_PASSWORD
dotnet run --launch-profile https
```

Введите пароль пользователя PostgreSQL. Ввод не отображается на экране. Оставьте терминал открытым. Дождитесь сообщения `Now listening on: https://localhost:7062`.

Откройте [Swagger](https://localhost:7062/swagger). При первом открытии браузер может предупредить о локальном сертификате разработки. Для Fedora сертификат можно установить командой `dotnet dev-certs https --trust`, затем перезапустить backend.

### 3. Запустите frontend

Откройте второй терминал:

```bash
npm run dev -- --host localhost --port 5173 --strictPort
```

Откройте [http://localhost:5173](http://localhost:5173). Оставьте оба терминала открытыми, пока пользуетесь сайтом. Для завершения нажмите **Ctrl+C** в каждом терминале.

### 4. Откройте рабочую панель и проверьте данные

- На лендинге нажмите **«Открыть админку»** или перейдите напрямую на `http://localhost:5173/admin`. Войдите по учетной записи сотрудника; адрес формы входа — `http://localhost:5173/admin/login`.
- Откройте раздел **«Операции и справочники»** для добавления, изменения и удаления гостиниц, рейсов, экскурсий, бронирований, финансовых и других записей. Связанные сущности указываются по ID существующего туриста, рейса, гостиницы, агентства или экскурсии.
- Раздел **«Туристы»** предназначен для ведения туристов; раздел **«Отчеты по ТЗ (1–15)»** — для формирования и экспорта отчетов.
- Для демонстрации отчетов введите период **15.10.2026–30.11.2026**. В базе есть синтетические группы на 15 октября и 6 ноября 2026 года, гостиничные бронирования, экскурсии, паспорта, дети, груз и финансовые операции.
- Для ежемесячного отчета выберите **октябрь 2026** или **ноябрь 2026**.
- Ежемесячный отчет показывает общую выручку и расходы из финансового учета отдельно от суммы продаж путевок.
- При записи ребенка на экскурсию укажите ID взрослого сопровождающего, ID экскурсии и ID ребенка. Сначала сопровождающий должен быть записан на эту же экскурсию.
- В разделе отчетов доступен рейтинг качества экскурсионных агентств; отчет о популярности экскурсий также учитывает записанных детей.
- В финансовом отчете можно выбрать ID группы (рейса) и категорию туристов. ID демонстрационной группы виден в результате отчета **«8. Загрузка рейсов»**.
- Для отчетов по экскурсиям используйте период **15.10.2026–30.11.2026**; для загрузки рейсов выберите даты, включающие **15.10.2026** и **06.11.2026**.

Если появляется `Port 5173 is already in use` или `address already in use`, сервер уже запущен. Не запускайте его второй раз: откройте сайт по указанному выше адресу или нажмите **Ctrl+C** в старом терминале. Если старый терминал недоступен, завершить только процессы приложения можно командой:

```bash
sudo fuser -k -TERM 5173/tcp 7062/tcp
```

## Архитектура клиентской части

- `src/lib/api.ts` — единый слой HTTP-запросов к backend с передачей защищенной cookie-сессии
- `src/pages/AdminLogin.tsx` — вход сотрудников в административную панель
- `src/pages/*` — отдельные экраны и бизнес-логика интерфейса
- `src/App.tsx` — маршрутизация лендинга и административных разделов
- `src/pages/OperationsManagement.tsx` — административное ведение операций и справочников
- `src/pages/Warehouse.tsx` — складские ведомости и учет грузов по туристам и рейсам
- `src/pages/ReportCenter.tsx` — выбор отчетов и формирование запросов к API
- `src/styles.css` — палитра, адаптивная оболочка и доступные анимации интерфейса

## Соответствие курсовому заданию

Для варианта №10 административный центр предоставляет отчеты по таможне, гостиницам, туристам, экскурсиям, рейсам, грузу и финансам, включая фильтрацию по параметрам и выгрузку CSV. Операционные разделы позволяют через API серверной части управлять туристами, гостиницами, рейсами, экскурсионными агентствами и записями на экскурсии, бронированиями, грузом, финансами, паспортами, детьми и поездками.

Запросы отчетов и CRUD-операции вызываются backend через процедуры PostgreSQL (`CALL`). Функции в `StoredProcedures.sql` и `CourseworkEnhancements.sql` содержат переиспользуемую SQL-логику; процедуры служат точками вызова для интерфейса и серверной части.

Лендинг доступен без входа. Для разделов `/admin/*` требуется учетная запись сотрудника с ролью `Admin`; backend дополнительно защищает API и хранит сессию в `HttpOnly` cookie. Учетные записи создаются администратором базы данных, публичной регистрации и пользовательского входа нет. Используйте приложение по HTTPS и не открывайте API в общедоступную сеть. При показе проекта запустите backend и frontend; адрес backend задается через `VITE_API_BASE_URL`.

## Проверка совместимости с pgAdmin/PostgreSQL

Если база уже существует и загружена из дампа, можно быстро проверить совместимость с backend через SQL-скрипт:

- `../Database/CompatibilityCheck.sql`

Он показывает, есть ли в PostgreSQL таблицы и поля, используемые в приложении: `employee_accounts`, `Bookings`, `Flights`, `Hotels`, `Tourist Information`, `Tourist Cargo`, `Finances` и др.

Для подключения из ASP.NET используйте строку вида:

```json
"ConnectionStrings": {
  "DefaultConnection": "Host=localhost;Port=5432;Database=\"Touristic Firma\";Username=postgres;Password=YOUR_PASSWORD;"
}
```

Если имя базы содержит пробелы, его обязательно экранировать кавычками в `Database=`.

Для демонстрации отчетов в существующую БД можно добавить синтетическую тестовую группу:

- `../Database/DemoData.sql`

Скрипт добавляет рейс `DEMO-TF-2026` и связанные записи туристов, гостиницы, багажа, экскурсии и финансов. Повторный запуск пропускает создание, если этот демо-рейс уже есть. Данные не заменяют реальную информацию.

## Рекомендации для курсового проекта

- Используйте реальный backend API, а не захардкоженные заглушки
- Держите все endpoint в конфиге через `VITE_API_BASE_URL`
- Не смешивайте сетевую логику напрямую в компонентах
- Добавляйте обработку ошибок и информирование пользователя
- Поддерживайте единый стиль и единообразный UX для всех разделов
